#### activity\_logs 테이블 (0007)

홈 화면의 자립 준비도는 "앱에서 실제로 해 본 것"으로 점수를 매깁니다. 예를 들어 주거 영역에는 "원룸 계약 연습을 해 봤나" 항목이 있습니다.

그런데 음성 연습과 한 달 살아보기는 앱 안에서만 돌아서, 서버는 사용자가 이걸 했는지 알 방법이 없었습니다. 그래서 앱이 연습이나 한 달 살아보기를 끝낼 때마다 서버에 알리고(`POST /users/{id}/activities`), 서버는 그걸 이 테이블에 한 줄씩 쌓습니다.

**실제로 쌓이는 모습**

| user\_id | kind | ref | data | created\_at |
| --- | --- | --- | --- | --- |
| (사용자 A) | practice | realestate | {"good": 3, "missed": 1, "score": 72} | 11-01 14:00 |
| (사용자 A) | month\_life | (빈칸) | {"income": 180, "left": 12, "shortage": 0, "used\_emergency": 0, "home": "STUDIO", "good": 5, "bad": 2, "bad\_events": \[...\]} | 11-01 15:00 |

**칼럼**

| 칼럼 | 타입 | 들어가는 것 |
| --- | --- | --- |
| id | BIGSERIAL PK |  |
| user\_id | UUID → users, 사용자 삭제 시 같이 삭제 | 누가 했나 |
| kind | VARCHAR(20) | 무엇을 했나. `practice` 음성 연습 · `month_life` 한 달 살아보기 |
| ref | VARCHAR(50) | 어떤 연습이었나. 상황 id (`realestate` 원룸 계약, `bank` 은행 계좌 등). 한 달 살아보기는 빈칸 |
| data | JSONB | 결과. 아래 표 참고 |
| created\_at | TIMESTAMPTZ | 언제 했나 |

**data 안에 들어가는 것**

| kind | 항목 |
| --- | --- |
| practice | `good` 챙긴 개수 · `missed` 놓친 개수 · `score` 점수(0~100) |
| month\_life | `income` 수입 · `left` 남은 돈 · `shortage` 모자란 돈 · `used_emergency` 쓴 비상금 (모두 만 원) · `home` 집 종류(STUDIO 원룸 · PUBLIC 공공임대 · SHARE 쉐어하우스) · `good`, `bad` 잘한 선택·아쉬운 선택 개수 · `bad_events` 아쉬운 선택을 한 사건 id |

한 달 살아보기 돈은 게임 속 가상 금액입니다.

**자립 준비도에서 쓰는 법**

- "원룸 계약 연습을 해 봤나": `kind = practice`, `ref = realestate`인 줄이 있으면 한 것
- "놓친 것 없이 대처"(안전): 수상한 전화 연습에서 `missed = 0`인 줄이 있으면 한 것
- "모자람 없이 한 달 버티기"(돈): `kind = month_life`이고 `shortage = 0`인 줄이 있으면 한 것

### 서류 위험 찾기 API

`POST /api/documents/risk-check`

AI는 서류에서 값과 근거 문장만 읽고, 위험 판정은 우리가 정한 규칙 파일(`app/doc_risk_rules.json`)대로 서버가 진행 합니다.

요청:

| 필드 | 필수 | 뜻 |
| --- | --- | --- |
| user\_id | O | 사용자 id |
| doc\_type | O | `registry` 등기부등본 · `lease` 임대차 계약서 · `labor` 근로계약서 |
| file\_base64 | O | 사진·PDF (약 10MB까지) |
| file\_name |  | 파일 이름 |
| context |  | 등기부등본과 맞춰 볼 계약 정보: 집주인 이름, 주소, 보증금, 집값(원) |

응답:

| 필드 | 뜻 |
| --- | --- |
| summary | 전체 판정(가장 나쁜 상태), 한 줄 요약, 상태별 개수 |
| findings\[\] | 규칙 하나당 판정: 상태, 근거 문장, 무슨 뜻인지, 할 일, 연결된 연습 |
| rules\_version | 규칙 파일 버전 |

상태:

`danger` 위험

`check` 확인 필요

`ok` 괜찮아요

`unknown` 서류에서 못 찾음

404 사용자 없음

422 형식 오류·파일 못 읽음

503 AI 오류

`app/doc_risk_rules.json` - 규칙은 총 22개입니다.

`presence` 있는지 확인

`match`다른 정보와 비교

`calc`는 서버가 다시 계산하는 규칙

| 서류 | 규칙 |
| --- | --- |
| 등기부등본 (8) | 진짜 주인인지 · 신탁 · 압류·가압류·경매 · 빚과 보증금이 집값의 70% 이상 (calc) · 전 세입자 보증금 미반환 · 주소 일치 · 90일 안에 주인 바뀜 (calc) · 7일 안에 뗀 등기부 (calc) |
| 임대차 계약서 (7) | 보증금 계좌가 집주인 이름인지 · 대리인 계약 · 전입신고 막는 특약 · 새 대출 막는 특약 · 계약 기간 (calc) · 관리비 · 수리 떠넘기기 |
| 근로계약서 (7) | 최저임금 2026년 10,320원 (calc) · 필수 내용 누락 · 주휴수당 주 15시간 (calc) · 그만두면 물어내라는 조항 · 월급날 · 3.3% 공제 · 쉬는 시간 (calc) |

### 롤플레잉 힌트 API

`POST /api/coach/roleplay/{scenario_id}/hint`.

앱은 상대 첫 말과 매 답변 뒤에 불러 화면 위 태그를 갱신합니다.

| 요청 필드 | 뜻 |
| --- | --- |
| history | 지금까지 대화 |
| stage, variant\_id, surprise\_ids | 사용자 단계, 이번 전개, 이번 돌발 상황 |

| 응답 필드 | 뜻 |
| --- | --- |
| label, example | 지금 챙길 것과 예시 말 ("뭐라고 하지?") |
| checks\[\] | 이 상황에서 챙길 것 목록과 챙겼는지 여부. 돌발 상황 대처는 상대가 꺼낸 뒤에만 들어감 |
| done, remaining | 다 챙겼는지, 남은 개수 |

### 음성 롤플레잉 개선 (#33, #35~#38)

음성 롤플레잉은 은행 창구, 집 계약, 알바 면접 같은 상황을 통화처럼 말로 연습하는 기능입니다. 사용자가 마이크로 말하면 AI가 상대 역할(직원·집주인 등)로 답하고, 끝나면 챙긴 것과 놓친 것을 채점합니다.

직접 테스트해 보니 "대화가 안 맞는다"는 문제가 많았고, 서버와 앱을 같이 고쳤습니다.

#### 한 번 말할 때 흐름

1. 앱이 마이크로 사용자 말을 글자로 바꿉니다 (안드로이드 음성 인식)
2. `POST /coach/roleplay/{id}/reply`로 보냅니다
3. 서버가 질문인지 판단하고, 상대가 이미 한 말을 표시해 AI에게 넘깁니다
4. AI 답이 앞에서 한 말과 거의 같으면 한 번 더 생성합니다
5. 대화를 끝낼지 서버가 정합니다 (AI가 혼자 끝내지 못하게)
6. 앱은 답을 자막으로 보여 주고, `hint`를 불러 챙길 것 태그를 갱신합니다

#### 서버에서 고친 것

| 문제 | 원인 | 고친 방법 | 위치 |
| --- | --- | --- | --- |
| 내가 질문했는데 상대가 엉뚱한 말을 함 | 음성 인식 글에는 물음표가 없어 AI가 질문인지 모름 | 끝말(~나요, ~까요)과 의문사(얼마, 언제)로 질문을 가려 `(질문)` 표시를 붙임. AI는 질문에 먼저 답함 | `coach/llm.py` `looks_question`, `voice_message` |
| "그렇군요" 하면 "등기요?" 처럼 낱말 하나를 되묻음 | AI가 끝낸 말 한 단어를 따라 함 | 프롬프트에 되묻기 금지 규칙 추가 | `coach/prompts.py` |
| 끝까지 안 했는데 갑자기 끝남 | AI가 대사를 다 했다고 혼자 끝냄 | 사용자가 마무리 말(감사합니다, 안녕히 등)을 하고 질문이 아닐 때만 끝냄. 대사 뒤에도 10번까지 더 이어갈 수 있음 | `llm.py` `ROLEPLAY_EXTRA_TURNS`, `_CLOSING_WORDS` |
| 상대가 같은 말을 또 함 | 앞에서 한 말을 기억 못 함 | 대화 40턴까지 넘기고, 이미 한 대사에 "(이미 함)" 표시. 답이 앞의 말과 70% 이상 같으면 한 번 다시 생성 | `llm.py` `_done_lines`, `repeats` |
| 상대가 기계적임 | 말투 규칙이 없었음 | 사람 같은 말투 규칙 추가, temperature 0.5 | `prompts.py` |
| 돌발 상황이 상황과 안 맞음 (아이가 뛰는 집인데 "공사 중") | 돌발 상황을 아무 전개에서나 뽑음 | 돌발 상황마다 어울리는 전개(`fits`)를 적고 그 전개에서만 나옴 | `roleplay.py` `pick_plan`, `roleplay_scenarios.json` |
| 돌발 상황이 갑자기 팱 튀어나옴 | 대화 초반에 바로 나옴 | 대화가 조금 이어진 뒤 나오게 하고, 앞 대화와 이어지게 꺼내도록 프롬프트 수정 | `roleplay.py` `lines_for`, `llm.py` |
| 챙긴 걸 말했는데 체크가 안 됨 | 음성 인식 띄어쓰기가 들쭉날쭉 ("필요 없" vs "필요없어요") | 띄어쓰기를 빼고 비교 | `roleplay.py` `feedback_items` |
| "이렇게 말해 보면 더 좋아요"에 내가 안 한 말이 나옴 | 상황별 예시를 그대로 보여 줌 | 내가 실제로 비슷하게 말한 것만, 내 말 그대로 보여 줌 | `roleplay.py` `my_better` |
| 연습 중에 뭘 챙겨야 하는지 모름 | 결과 화면에서만 알 수 있었음 | `hint` 응답에 `checks` 추가. 돌발 상황 대처는 상대가 꺼낸 뒤에만 보임 (미리 알려 주지 않음) | `roleplay.py` `progress`, `services/roleplay.py` |

점수: 챙긴 항목 비율 × 90 (돌발 상황 대처는 2배) + 끝까지 대화하면 10점

#### 상황을 추가·수정할 때

- 대사, 챙길 것(키워드), 돌발 상황은 모두 `roleplay_scenarios.json`에 있습니다. 코드를 고칠 필요는 없습니다
- 돌발 상황의 `fits`에는 같은 상황의 전개 id만 넣습니다. 비워 두면 모든 전개에서 나옵니다
- 챙길 것 키워드는 사용자가 실제로 말할 법한 표현으로 여러 개 넣습니다. 띄어쓰기는 신경 쓰지 않아도 됩니다
- 자세한 데이터 형식은 `docs/roleplay.md`에 있습니다

### 한 달 살아보기

"80억 인구 중 한 명으로 살아보기" 같은 인생 시뮬레이션 게임에서 영감을 받은 기능입니다. 자립을 하면 어떤 한 달을 보내게 될지, 실제 돈을 쓰기 전에 게임처럼 미리 살아 보는 것이 목표입니다.

**생활비 시뮬레이션과 다른 점**

|  | 생활비 시뮬레이션 | 한 달 살아보기 |
| --- | --- | --- |
| 하는 것 | 수입을 주거·식비 등 항목별로 나눠 보고 부족한 곳을 확인 | 정한 예산으로 4주를 직접 살며 그때그때 선택 |
| 느낌 | 계획표 짜기 | 게임처럼 일이 터지고 결과를 겪음 |
| 서버 | 결과를 `simulations`에 저장 | 앱 안에서만 계산, 끝난 뒤 요약만 `activity_logs`에 저장 |

**어떻게 진행되나**

1. 시작 조건 고르기: 한 달 수입(90·120·150·180만 원), 사는 곳(원룸 월세·공공임대·쉐어하우스), 따로 떼 둘 비상금(0·10·20·30만 원)
2. 주거비·통신비가 먼저 나가고, 매주 식비·교통비가 나갑니다
3. 매주 확률에 따라 일이 생깁니다. 감기, 친구 생일, 관리비 고지서, 보일러 고장, 한정 특가, 알바 추가 근무, 택배 문자 사기, "무직자 바로 대출" 광고 등 25가지
4. 일마다 선택지를 고릅니다. 고른 것에 따라 돈이 늘거나 줄고, 다음 주에 영향이 남기도 합니다
5. 생활비가 모자라면 비상금에서 먼저 빠지고, 그래도 모자라면 "부족한 돈"으로 남습니다
6. 4주가 끝나면 결과 화면: 남은 돈, 비상금 사용, 부족한 돈, 잘한 선택·아쉬운 선택, 팁

**앱의 다른 기능과 이어짐**

결과 화면에서 아쉬운 선택에 맞는 다음 할 일을 권합니다.

| 한 달 동안 있었던 일 | 권하는 것 |
| --- | --- |
| 택배 문자 사기에 속음 | 수상한 전화 대처 연습 (롤플레잉) |
| 대출 광고에 넘어감 | 급할 때 안전하게 돈 구하는 법 상담 |
| 돈이 모자랐거나 비상금을 씀 | 긴급 생활비 지원 찾기 |
| 보일러 고장·관리비 문제 | 집주인에게 수리 요청 연습 |
| 알바비가 밀림 | 밀린 알바비 받기 연습 |
| 감기·부상·치과 | 의료비 지원 찾기 |
| 원룸에 살았음 | 청년 월세 지원 찾기 |

금액은 모두 예시 기준의 가상 값이고, 사용자의 실제 수입·지출은 받지 않습니다.

결과는 자립 준비도의 돈·안전·생활 영역에 반영됩니다 (모자람 없이 한 달 버티기, 사기 피하기, 한 달 살아보기 1번·2번).

| --- | --- | --- | --- |

| 중간 | AI 호출 횟수 제한 | 상담·롤플레잉·서류 읽기는 부를 때마다 OpenAI 비용이 나는데 제한이 없음 | 사용자별 1분에 N번 제한, 넘으면 429 (`cache.py`처럼 서버 메모리로 충분) |
| 중간 | 예상 못 한 오류 | 오류 처리기가 정해 둔 오류 3종류만 있어, 그 밖의 500 오류는 다른 형식으로 나가고 내용도 남지 않음 | `errors.py`에 나머지 오류 처리기 추가: 로그를 남기고 같은 오류 형식(`INTERNAL_ERROR`)으로 응답 |
| 중간 | AI가 안 될 때 대신할 것 | 정책 검색은 AI 검색(RAG)이 실패하면 503만 돌려줌. OpenAI가 느리거나 키가 만료되면 상담 화면에서 정책을 하나도 못 찾음 | 서버에 이미 있는 키워드 검색(rag\_mock.py)으로 대신 결과를 돌려주고 "간단 검색 결과"라고 표시. 상담 AI 담당과 협의 |
| 낮음 | 응답 시간 기록 | 어떤 API가 얼마나 느린지 남지 않음 | main.py에 요청별 처리 시간을 로그로 남기는 미들웨어. 느린 API를 찾고, 발표 때 "평균 응답 n초" 근거로 씀 |
| 낮음 | 가입 중복 | POST /users를 부를 때마다 새 사용자가 생김. 앱을 다시 깔면 기록이 남은 이전 계정을 찾을 방법이 없음 | 사용자 확인(토큰)을 넣을 때 같이: 휴대폰 번호 등으로 이전 계정 되찾기 |
| 낮음 | 목록 길이 | 성장 기록이 시뮬레이션·연습을 전부 돌려줌 | 최근 N개만 돌려주거나 페이지 나누기 |
| 낮음 | 인덱스 | `documents.policy_id`, `documents.checklist_item_id`에 인덱스가 없어 정책·체크리스트 지울 때 서류를 전부 훑음 | 두 칼럼에 인덱스 추가 |

#### (선택) 보호자(담당자) 페이지 API

페이지 자체(웹 화면)는 따로 만들어야 합니다. 아래는 그 페이지와 앱이 쓸 API입니다.

| API (예시 경로) | 누가 씀 | 하는 일 |
| --- | --- | --- |
| `POST /api/users/{id}/guardian-invites` | 앱 (청년) | 연결 코드 만들기. 보여 줄 항목(scopes)을 고름 |
| `GET /api/users/{id}/guardians` | 앱 (청년) | 내가 연결한 담당자 목록 |
| `DELETE /api/users/{id}/guardians/{gid}` | 앱 (청년) | 연결 끊기 (status = revoked) |
| `POST /api/guardian/signup`, `/login` | 페이지 (담당자) | 담당자 가입·로그인, 토큰 발급 |
| `POST /api/guardian/links` | 페이지 (담당자) | 연결 코드 입력 → 연결 (만료·잘못된 코드는 거절) |
| `GET /api/guardian/users` | 페이지 (담당자) | 맡은 청년 목록: 이름, 자립 준비도, 가장 약한 영역, 다가오는 마감 수, 마지막 활동일 |
| `GET /api/guardian/users/{id}` | 페이지 (담당자) | 한 명 상세: 영역별 준비도, 체크리스트 진행, 다가오는 마감, 최근 연습. 허락한 항목(scopes)만 |

담당자 화면에서 가장 쓸모 있는 건 "오래 활동이 없는 청년", "마감이 곧인데 준비가 안 된 청년"을 먼저 보여 주는 것입니다. 목록을 이 순서로 정렬합니다.

#### API 응답 속도 개선

지금도 gzip 압축, 고정 데이터 캐시, 정책 검색 캐시(`cache.py`)는 들어가 있습니다. 그 외에 해 볼 만한 것입니다.

| 무엇 | 지금 | 고칠 방법 |
| --- | --- | --- |
| 성장 기록 화면 요청 수 | 성장 기록 화면이 성장 기록과 자립 준비도를 따로 불러 서버를 두 번 다녀옴 (타임라인도 준비도를 따로 부름) | 성장 기록 응답에 자립 준비도를 같이 넣기 |
| 자립 준비도 계산 | 볼 때마다 활동 기록·연습 기록·서류·체크리스트를 전부 다시 읽어 계산 | 사용자별로 결과를 잠깐 저장하고, 활동·연습·체크가 생길 때만 다시 계산 (위 `readiness_snapshots`와 같이 하면 됨) |
| 정책 상세 | 정책 상세·쉬운 말·작성 도우미는 잘 안 바뀌는데 매번 새로 받음 (`no-cache`) | 사용자별 자격 표시를 뺀 부분만 서버 캐시에 담기 |
| 느린 API 찾기 | 어느 API가 느린지 모름 | 요청별 처리 시간 로그 (위 개선할 점의 "응답 시간 기록")로 먼저 재고, 제일 느린 것부터 |

### 같이 정해야 할 것

- 알림을 앱 안 목록만 할지, 푸시까지 할지
- "하루 한 번 실행"을 어디서 돌릴지 (서버 안 스케줄러, 또는 서버 밖 cron)
- 정책 담당에게 받을 날짜 데이터의 형식
